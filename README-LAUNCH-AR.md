# حُرّ HUR — ملاحظات النسخة المحسّنة

## إعداد Cloudflare Pages
- Build command: `npm run build`
- Build output directory: `dist`
- Root directory: `hurr-perfumes-main` (إذا كان المشروع داخل مجلد بهذا الاسم في المستودع)
- أضف `VITE_SUPABASE_URL` وواحدًا فقط من `VITE_SUPABASE_ANON_KEY` أو `VITE_SUPABASE_PUBLISHABLE_KEY` إلى بيئة Production.

## التغييرات
- تحسين استجابة رأس الموقع والأقسام على الهواتف ومنع تمدد الصفحة أفقيًا.
- جعل جداول الإدارة قابلة للتمرير أفقيًا داخل الحاوية على الشاشات الضيقة.
- حذف مجلد `dist` القديم من حزمة المصدر حتى يُنشأ بناء جديد عند النشر.
- إضافة fallback لـ SPA عبر `public/_redirects` كي تعمل المسارات مثل `/admin` عند فتحها مباشرة.
- مواءمة تحويل المنتج مع مخطط جدول المنتجات المنشور (name/slug/description/price/image_url/stock/is_active)، وإضافة حقل category عبر ترحيل SQL مرفق؛ لا تُرسل أعمدة العرض غير الموجودة في الجدول.
- إبقاء كتالوج المنتجات فارغًا افتراضيًا؛ لا توجد أسعار أو منتجات تجريبية مضافة محليًا.
- نقل نسخة مرجعية من SQL إلى `supabase/schema-reference.sql` وعدم نشرها كملف عام داخل `public`.

## ملاحظات قبل الإطلاق
- لا تُشغّل ملف schema المرجعي كاملًا فوق قاعدة بيانات إنتاجية قائمة دون مراجعة؛ لا حاجة إلى إعادة إنشاء الجداول الحالية.
- اختبر تسجيل الدخول، إضافة منتج حقيقي، إنشاء طلب، وتتبعه بعد نشر Production.


## إعداد الطلبات الآمنة (مهم قبل استقبال طلبات حقيقية)

1. أضف `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY` في إعدادات بناء الموقع، ثم أعد البناء والنشر. لا تضع مفتاح `service_role` داخل متغيرات `VITE_` أو داخل كود المتصفح.
2. في لوحة Supabase، فعّل تسجيل الدخول المجهول من إعدادات Authentication إذا كنت ستبقي `verify_jwt = true` للدالة؛ الواجهة تنشئ جلسة مجهولة قبل إرسال الطلب.
3. انشر الدالتين من جذر المشروع باستخدام Supabase CLI: `supabase functions deploy create-order` و`supabase functions deploy track-order`.
4. تأكد من وجود أسرار الخادم `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY` في بيئة Edge Functions. المفتاح السري للخادم لا يُضاف أبدًا إلى ملفات الواجهة أو المستودع.
5. نفّذ `supabase/migrations/202610280001_hurr_categories_and_order_compat.sql` في SQL Editor أولًا؛ هذا الترحيل يضيف القسم ويحدّث دالة إنشاء الطلبات لتناسب جدول المنتجات المبسّط. راجع النسخة الاحتياطية قبل أي تغيير على قاعدة حية.
6. اختبر إنشاء طلب تجريبي من الموقع ثم راجع `Supabase → Edge Functions → create-order → Logs` عند الفشل. الرسائل في الواجهة أصبحت تميز مشاكل الاتصال عن رفض JWT وأخطاء قاعدة البيانات قدر الإمكان.

## إصلاحات نسخة حُرّ الحالية
- حفظ فئة المنتج `category` فعليًا في قاعدة البيانات واستعادتها عند تحميل المنتجات، بدل إظهار كل المنتجات على أنها عطور للجنسين.
- حفظ رابط صورة المنتج في `image_url` المتوافق مع جدول المنتجات المنشور، مع معاينة الرابط والتحقق من أنه HTTP/HTTPS.
- توليد معرّف للمنتج الجديد قبل الإدراج لأن عمود `products.id` نصي ولا يملك قيمة افتراضية في المخطط المرجعي.
- عدم إغلاق نافذة إضافة/تعديل المنتج إلا بعد نجاح الحفظ في Supabase.


## إصلاح خطأ إتمام الطلب في نسخة 28 أكتوبر 2026
- أعيد بناء `src/context/StoreContext.tsx` لأن نسخة GitHub كانت قد اختُزلت إلى دالة إضافة الكوبون فقط، فحُذفت منها وظائف السلة والطلبات والسياق التي تعتمد عليها معظم الواجهة.
- يدعم `placeOrder` الآن استجابتي خدمة الطلبات `{ id, trackingToken, ... }` و`{ success: true, order: { id, trackingToken, ... } }`؛ وهذا يمنع اعتبار الطلب الناجح فاشلًا عند تغليف البيانات داخل `order`.
- تحديث حالة الطلب في لوحة المدير يستخدم `select('id').maybeSingle()` حتى لا تعلن الواجهة نجاحًا إذا لم يُحدّث أي صف، ويعرض تفاصيل خطأ قاعدة البيانات في وحدة التحكم.
- لم تتم إضافة `PATCH` بعد إنشاء الطلب؛ دالة قاعدة البيانات تنشئ الطلب وتخصم المخزون ضمن معاملة واحدة، ويجب ألا تكتب الواجهة الطلب نفسه مرة ثانية.
